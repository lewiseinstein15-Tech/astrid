# Writing clear docs

Write for the tired engineer who needs an answer, not an essay:

1. Lead with the answer. The first sentence of a section states what it is or what to do; explanation follows, never precedes.
2. One idea per paragraph, three to five sentences. If a heading is followed by two lines, either deepen it or merge it.
3. Concrete beats general: real names, real commands, real numbers. A reader should be able to copy-paste every code block and command.
4. Explain terms on first use; never introduce an acronym without expansion.
5. State constraints explicitly — versions, operating systems, limits — instead of letting readers discover them by failure.
6. No filler conclusions ("in summary, this document showed...") and no unmarked placeholders; if a fact is unknown, say so and mark it.
7. Prefer examples over adjectives: show the good case and the failure case side by side.
8. End on the last substantive section. Completion notices and restated introductions are cut, not written.
